# COMPATIBILITY

This repo depends on Azure features that are preview or newly GA, and on ARM
API versions that are still -preview even where the feature is GA. This file
tracks what we depend on, what we have pinned, and when each claim was last
verified against Microsoft documentation.

Rules:
- Every azapi resource in /infra pins an explicit ARM API version and has a
  row here.
- Any PR that adds or changes a pin updates this file in the same PR.
- "Last verified" means a human or agent checked the linked doc on that date,
  not that the doc was published then.
- If CI or a live test breaks because a preview surface changed, the fix PR
  updates this table and notes the breakage under History.

| MCP tools/call denial wire shape (protocol, not Azure-specific) | VERIFIED against modelcontextprotocol.io 2025-06-18 | The spec's Tools page ("Error Handling") defines exactly two categories: Protocol Errors (standard JSON-RPC 2.0 error object, e.g. `{"jsonrpc":"2.0","id":3,"error":{"code":-32602,"message":"Unknown tool: ..."}}`) and Tool Execution Errors (`CallToolResult` with `isError:true`, reserved for failures during actual tool execution). The normative wording is a SHOULD, and it lives in the schema, not the prose page: `schema/2025-06-18/schema.ts` says "Any errors that originate from the tool SHOULD be reported inside the result object, with `isError` set to true, _not_ as an MCP protocol-level error response", with the stated rationale "Otherwise, the LLM would not be able to see that an error occurred and self-correct". PRECISION CORRECTION 2026-08-08, after a re-verification pass found this row conflated two different things: the two-category split above IS from the spec, but the choice of WHICH category a per-tool authorization denial belongs to is NOT. The 2025-06-18 spec does not settle that question. Naming the nearest counter-evidence rather than claiming pure silence, because a skeptical reader will find it: the authorization section carries an error table whose 403 row reads "Invalid scopes or insufficient permissions", and a per-tool denial is arguably insufficient permissions. That table is read here as governing the HTTP status of OAuth 2.1 TOKEN validation rather than the JSON-RPC reporting channel of a tool-level decision, for two reasons: the section scopes itself to authorization "at the transport level", and its sibling rows ("Authorization required or token invalid", "Malformed authorization request") are all token-lifecycle cases evaluated before any MCP method is dispatched. On the tool side the spec says only "implement proper access controls", with no reporting-channel guidance at all. That reading is a judgement, not a quotation. So the sentence that previously read "so it is a Protocol Error" was this repo's DESIGN INFERENCE presented as a spec consequence. The design decision stands and is deliberate: a gateway-side denial happens before any tool executes, so nothing "originated from the tool", and the JSON-RPC error object with the request `id` echoed is the natural shape (Streamable HTTP requires a JSON-RPC response, success or error, for every well-formed request; HTTP 401/403 pre-envelope is reserved for transport/session violations). But it is a choice this repo made, not a rule the spec imposed, and the backend's contrasting `isError` shape is equally spec-compliant. The spec does not mandate a numeric code for "not authorized for this tool"; issue-18's fragment uses a custom code in the MCP-reserved range (-32000 to -32099) rather than reusing -32602 ("Unknown tool"), which would misdescribe a mapped-but-under-entitled denial. Also corrected: the spec names no HTTP status for a well-formed `tools/call` the server answered (the transport section enumerates only 202, 400, 404, 405), so "HTTP 200 for an isError result" is an inference from the absence of any 4xx rule plus live observation, not a quoted spec mandate. Re-check trigger: if a later spec revision adds guidance on the reporting channel for per-tool authorization denial, or names a status code for an answered `tools/call`, revisit both this row and `infra/terraform/modules/apim-mcp-server/policies/mcp-server.xml`'s deny-shape comment. https://modelcontextprotocol.io/specification/2025-06-18/server/tools#error-handling and https://modelcontextprotocol.io/specification/2025-06-18/basic/transports | 2026-08-06 |

THE SPEC BACKING DIFFERS BETWEEN THE TWO CASES AND THE DIFFERENCE IS STATED RATHER THAN SMOOTHED OVER, because presenting a design inference as a spec consequence is the exact error the row above had to correct on 2026-08-08. Case A, NO `id` field: QUOTED, the citation is squarely on point. A body carrying a `method` and no `id` is by the spec's own typology a NOTIFICATION ("Notifications MUST NOT include an ID", Base Protocol > Notifications), and the Streamable HTTP transport's step 4 governs precisely that input ("If the input is a JSON-RPC response or notification"), saying "If the server cannot accept the input, it MUST return an HTTP error status code (e.g., 400 Bad Request). The HTTP response body MAY comprise a JSON-RPC error response that has no id." Case B, an explicit `"id": null`: INFERENCE, by analogy to case A, NOT a quotation. That message is neither a valid request (the ID "MUST NOT be null") nor a valid notification (it carries an `id` key), so transport step 4 does not cleanly reach it, and step 5, which governs requests, says only that the server returns `text/event-stream` or `application/json` -- it names no error status at all. Answering case B identically to case A is this repo's deliberate choice for a message shape the spec leaves unaddressed. Error code -32600 "Invalid Request" ("The JSON sent is not a valid Request object.") is the standard JSON-RPC 2.0 code for this case (https://www.jsonrpc.org/specification), deliberately not -32001 (this repo's unchanged per-tool authorization code) or -32602 (the SDK's "Unknown tool" shape, row above): this is neither an authorization denial nor a missing tool, it is a malformed request the gateway never got far enough to authorize. The fix references `Newtonsoft.Json.Linq.JTokenType` unqualified in the policy expression; confirmed on APIM's own "`.NET Framework types allowed in policy expressions`" table (Supported members: All), the same allow-list `JObject` already relies on elsewhere in this file. The fix itself was proven live by run 31387242227 (2026-08-10), which is the run that verified it: both cases return HTTP 400 with `{"jsonrpc":"2.0","error":{"code":-32600,...}}` and no `id` key, the malformed-JSON case still 500s, and the gate's check (i) assertion passed. Do not read the earlier run 31381168415 as evidence of the fix; that run PRE-dates it and is the one that showed `"id":null` on the wire. ## Registry drift vs documentation drift

The pins below can go stale in two independent ways, owned by two separate,
non-overlapping mechanisms.

- Registry drift: a newer version of a pinned package (NuGet package, Terraform
  provider, or registry module including AVM) has been published. This is
  Dependabot's job (`.github/dependabot.yml`, issue #64). Because a raw bump PR
  edits only the manifest and would leave the row beside it stale, the required
  `compat-sync` status check (`.github/workflows/compat-sync.yml`) fails any
  `dependencies`-labelled PR that does not also update this file, naming the pin
  row that needs a fresh doc link and Last-verified date. Dependabot PRs are
  never `auto-merge-ok`; they touch /src, /infra, or /.github and go through
  governance review like any other pin change.
- Documentation drift: the documented contract of a fixed pin has changed under
  it (a feature moved preview -> GA, an ARM api-version behaviour or payload
  shape changed) even though the pinned version number has not moved. This is
  the compat-drift agent's job (`.github/workflows/compat-drift.yml`, issue #4),
  which re-checks the `Re-check trigger:` notes in this file against Microsoft
  Learn. It never edits this file; it opens a `drift-candidate` issue.

A pin can be the latest published version (Dependabot content) while its
documented behaviour has drifted (doc-drift agent's concern), and vice versa.

Honest limits of the registry-drift half (Dependabot does NOT cover these; they
stay doc-drift-agent or manual territory):

- ARM api-version strings embedded in azapi resource bodies (e.g.
  `2025-09-01-preview`). Not a provider or module version; Dependabot cannot see
  them.
- Transitive pins we do not directly reference (e.g. `ModelContextProtocol
  0.4.0-preview.3`, pulled via the preview Mcp.Sdk package). Dependabot bumps the
  direct parent only.
- The Terraform CLI pin (`.terraform-version` / compositions' `required_version`).
  The terraform ecosystem updates provider and module versions, not the CLI
  version.
- Prerelease NuGet pins (the `-preview` rows): Dependabot proposes a prerelease
  update only for a dependency already on a prerelease, so the stable pins are
  not dragged onto preview. Confirm this behaviour on the first real bump PR
  before relying on it.

- 2026-08-09: The azurerm ignore rule added on 2026-08-04 was a no-op, and
  Dependabot re-proposed azurerm 5.0.1 in PRs 72 and 91. The rule used
  `update-types: version-update:semver-major`. Dependabot can only evaluate an
  update-type condition when it can resolve the dependency's current version,
  and for a `~> 4.80` constraint it resolves that version from
  .terraform.lock.hcl. The two scenarios have a lock file and were correctly
  skipped. The two wrapper modules under infra/terraform/modules have none, so
  the current version was nil, the condition produced no ignored ranges, and
  the rule did nothing there. The PRs show the same split: both touched only
  the two module directories and never the scenarios, although all four
  declare the same `~> 4.80` constraint. Fixed by replacing the condition with
  `versions: [">= 5.0.0"]`, which Dependabot applies whether or not a current
  version resolves, and which still lets 4.x minor and patch bumps through.
  Verified by reading dependabot-core, in four files that form one chain:
  terraform/lib/dependabot/terraform/file_parser.rb (determine_version_for
  falls back to the lock file for any constraint not starting with a digit, so
  a lock-less directory yields a nil version);
  common/lib/dependabot/config/ignore_condition.rb (versions_by_type returns
  an empty list when that version is nil, while ignored_versions appends the
  `versions` array unconditionally);
  common/lib/dependabot/update_checkers/base.rb line 223 (ignore_requirements
  is built from ignored_versions alone); and
  terraform/lib/dependabot/terraform/update_checker.rb line 140
  (`versions.reject! { |v| ignore_requirements.any? { |r| r.satisfied_by?(v) } }`,
  which filters CANDIDATE versions). The last two are the load-bearing pair:
  neither reads dependency.version, which is precisely why a `versions` range
  works without a lock file and an update-type condition does not.
  terraform/lib/dependabot/terraform/requirement.rb parses `>=` ranges, so
  `>= 5.0.0` is a valid ignore string for this ecosystem.

  array verbatim when security_updates_only is set, so a `versions` ignore
  also suppresses SECURITY updates in its range while an update-types ignore

  route yet, but it is a real widening of the rule's reach.
